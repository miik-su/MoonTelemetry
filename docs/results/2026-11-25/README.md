# 2026-11-25 恢复与一小时混合负载检查

## 一小时独立进程混合负载

Windows x64 / MSVC / Native，三个客户端在同机向独立 Collector 进程发送合成
日志、指标和链路。Collector 以 OTLP/HTTP JSON 将三种信号发送到两个接收目标。
每个客户端在每次请求完成后暂停 25 毫秒。实际负载持续 3,600.003 秒。
源码为 `aad2836eb33c43bc9206ee786e6d172137f92341`，启动时工作区干净。
此提交与 `v0.1.4-rc.1` 的差异仅为验证文档和结果文件。

| 信号 | 请求 | 收到的记录 | 目标一送达 | 目标二送达 |
| --- | ---: | ---: | ---: | ---: |
| Logs | 114,650 | 458,600 | 458,600 | 458,600 |
| Metric points | 114,645 | 573,225 | 573,225 | 573,225 |
| Spans | 114,712 | 344,136 | 344,136 | 344,136 |
| 合计 | 344,007 | 1,375,961 | 1,375,961 | 1,375,961 |

拒绝请求和传输／响应错误均为 0。两个接收端实际计数均与 Collector 各出口
送达计数一致。Collector CPU 时间增量为 580,343 毫秒。3,566 个 RSS 采样中，
最高值为 11,345,920 字节。资源测量仅针对 Collector 进程，负载与接收端仍
与其共用主机。该轮使用固定合成样本，属于守恒与资源观察，不代表吞吐上限。
此版本的采样记录包含 RSS，队列与预算趋势由后续工具版本记录。

## 故障与恢复

验证源码 `a8fb17fb711d0d0fd00cb8aeb296331c1f613409`。
工具链为 moon 0.1.20261104 / moonc 0.10.20+65efd5b93，Native。

| 检查 | 实际观察 |
| --- | --- |
| OTLP 连接恢复 | Windows/MSVC 定向测试通过。接收端两次读取请求后关闭连接，导出器仅重试一次，计入一条拒绝。接收端恢复后，下一批成功且预算归零。 |
| Linux 满盘恢复 | GitHub Ubuntu Runner 的 64 KiB 独立 tmpfs 写满后，一个已接收记录在文件出口计入丢弃。释放占位文件后，下一条记录成功写出。 |
| Linux 退出与重启 | SIGINT、SIGTERM 下待处理记录均成功写出。强杀及重启用例确认易失记录不会自动恢复。 |

证据见 [Linux 工作流](https://github.com/miik-su/MoonTelemetry/actions/runs/45557780003)
和[日志原始 JSON](linux-faults.raw.json)。满盘用例实际写满小型测试挂载，
并通过 Collector 入口与真实文件出口验证。主机卷耗尽、保留策略和服务恢复
仍取决于目标部署配置。

```sh
moon test tests/integration/exporter_recovery_test.mbt --target native
```

Linux 工作流通过 `MOONTELEMETRY_TEST_TMPFS=1` 启用挂载用例，
普通本地测试无需挂载权限。只执行关键测试。
